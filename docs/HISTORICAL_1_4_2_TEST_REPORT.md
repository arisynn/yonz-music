# Yono Music 1.4.2 — shuffle and decorative artwork

Actual current verification: **113 JVM tests passed; 5 distinct Android tests passed on API29**. Debug assembly and lint passed. No uninstall or clear-data was used; the existing Dev app was upgraded from code8 to code9, Room schema3. Exact favorite, playlist, membership and selected-source rows were retained. Evidence: docs/verification/v1.4.2.

The baseline regression ran before the production fix: enabling shuffle at index4 of an eight-song queue left only five reachable songs ([4,5,3,7,1]) before the repeat-off endpoint. The old queue UI also displayed physical insertion order instead of playback order. This does not mean Media3 lacked randomization; it meant the visible queue was misleading and enabling shuffle could leave many songs behind its cursor.

The corrected real-service regression starts from indices4/7/2, checks every occurrence is reachable once, follows every Next through the actual controller, and checks the UI state’s order against the authoritative Media3 timeline. It also replaces a queue while shuffle stays enabled, preserves the requested seek position, actually decodes/plays a bundled original WAV, exercises end-of-audio automatic transitions, repeat-all wrapping, repeat-one restarting, and Next through a second media controller. No external audio service is used by these tests.

The existing queue regression passed move, duplicate occurrence identity, remove/Undo, preventing manual ordering while shuffled, and ignoring Undo from a replaced queue. Two updater tests still reproduce the old NaN constructor exception and render forty completed/unknown/verifying UI transitions without the corrected UI crashing. JVM coverage adds empty/single/two-song safety, complete unique permutations from every starting index and different shuffle cycles.

The Home change is decorative: a six-second local-artwork carousel and 600ms crossfade, no click or playback handler. It uses the existing size-aware bitmap cache and checks at most24 unique local artwork candidates. Missing artwork is skipped; no new remote lookup. Hidden/background state and reduced motion stop the carousel. Large-font layouts retain the existing text-first layout. The carousel instrumentation test renders the actual HomeIdentity composable with two original solid-colour local PNG fixtures, checks rendered screenshot pixels change, verifies no app click target, then verifies a static cover for longer than six seconds with Reduce motion enabled. Fixture covers are not inserted into the library. Full-app screenshots are recorded separately.

The software emulator initially showed an Android System UI ANR; selecting Wait recovered it without clearing Yono data. This environment event is distinct from a confirmed app crash. The historical Python/download suites were not rerun because this patch changes neither acquisition engine nor dependency versions. No live downloading, physical HyperOS/Android16, Bluetooth headset hardware, or independent Play Protect classification is claimed. Previous verification is archived in docs/HISTORICAL_1_4_1_TEST_REPORT.md and earlier reports.

The final five-case run passed shuffle, queue and both updater cases, but the rotation expectation failed because the emulator had global animator/transition/window scales set to0. This was the expected static product behavior under system reduced motion. Without changing the APK, the carousel case was rerun after enabling animations on the test emulator and passed. The failed and successful raw logs are retained. To exercise the rotating case, use an animation-enabled emulator profile (`adb shell settings put global animator_duration_scale 1`); do not infer device verification from these fixtures.

Cover is intentionally hidden in the existing large-font text-first layout.
